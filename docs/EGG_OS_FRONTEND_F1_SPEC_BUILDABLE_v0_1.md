## 3. Auth Store (Zustand)

```typescript
type AuthState = {
  accessToken: string | null
  user: {
    id: string
    email: string
    fullName: string
    companyId: string
    roles: string[]           // dari JWT claims — hint only
    firstLoginRequired: boolean
  } | null
  permissions: string[]       // dari /auth/me/permissions — source of truth
  activeRole: string | null   // role yang sedang aktif di switcher
  setAuth: (token: string, user: AuthState['user']) => void
  setPermissions: (perms: string[]) => void
  setActiveRole: (role: string) => void
  clear: () => void
}
```

- `accessToken` di memory, TIDAK pernah ke localStorage
- `permissions` di-fetch setelah login sukses via `/auth/me/permissions`
- `activeRole` default = role pertama dari JWT claims (tertinggi per hierarchy)

## 4. API Client + Silent Refresh

```typescript
// lib/api.ts
// Interceptor urutan:
// 1. Request: inject Authorization: Bearer {accessToken}
// 2. Response 401: panggil /auth/refresh (sekali, dengan mutex)
// 3. Kalau refresh sukses: update store + retry original request
// 4. Kalau refresh gagal: clear store + redirect /login
// MUTEX penting: kalau ada 3 request parallel yang 401 bersamaan,
// refresh cukup dipanggil sekali, 3 request nunggu hasilnya.
```

Implementasi mutex: `p-mutex` atau simple promise ref (`let refreshPromise: Promise | null`).

## 5. Routing + Guards (TanStack Router)

```
/                     → redirect: authenticated? /dashboard : /login
/login                → public, redirect ke /dashboard kalau sudah login
/dashboard            → protected, redirect ke view sesuai activeRole
/dashboard/spv        → require: hasPermission('dashboard.spv') atau role SPV_OUTLET
/dashboard/executive  → require: hasPermission('dashboard.executive') atau MANAGER/DIREKSI
/dashboard/inventory  → require: hasPermission('dashboard.inventory')
/dashboard/approval-queue → require: hasPermission('dashboard.approval_queue')
```

Guard pattern (TanStack Router `beforeLoad`):
```typescript
beforeLoad: ({ context }) => {
  if (!context.auth.accessToken) throw redirect({ to: '/login' })
  if (!context.auth.hasPermission('dashboard.spv')) throw redirect({ to: '/dashboard' })
}
```

## 6. Login Flow (urutan eksak)

```
1. User submit form (email + password)
2. POST /auth/login → { accessToken, user: {...} }
3. Simpan accessToken ke store (memory)
4. Decode JWT → ambil roles[] sebagai hint
5. GET /auth/me/permissions → simpan permissions[] ke store
6. Cek firstLoginRequired:
   - true → redirect /change-password (out of scope F1, tapi route harus ada sebagai placeholder)
   - false → redirect /dashboard
7. /dashboard → detect activeRole → redirect ke view yang sesuai
```

Error states yang harus di-handle di form:
- 401 ERR_INVALID_CREDENTIALS → "Email atau password salah"
- 403 ERR_USER_INACTIVE → "Akun tidak aktif, hubungi administrator"
- 429 ERR_LOGIN_LOCKED → "Terlalu banyak percobaan. Coba lagi dalam {lockedUntil}"
- Network error → "Tidak dapat terhubung ke server"

## 9. Acceptance Criteria

```
F1a  Login sukses → token di memory, TIDAK di localStorage → redirect dashboard
F1b  Login gagal: 401/403/429 → pesan error yang benar di form
F1c  Token expire mid-session → silent refresh → user tidak sadar
F1d  Refresh gagal → redirect /login + store cleared
F1e  Role SPV_OUTLET → landing di /dashboard/spv, view SPV
F1f  Role MANAGER → landing di /dashboard/executive
F1g  Role DIREKSI → landing di /dashboard/executive (bukan spv)
F1h  Multi-role user → role switcher tampil, switch berhasil ganti view
F1i  User tanpa permission dashboard → redirect /login (atau 403 page placeholder)
F1j  firstLoginRequired=true → redirect /change-password (placeholder page cukup)
F1k  Reload halaman → session hilang (memory cleared), redirect /login
F1l  Dashboard data load: skeleton saat loading, data tampil, error + retry kalau gagal
```

### Brand Mapping (hardcode MVP — utang: field color_config di DB)
```typescript
// src/lib/brand-theme.ts
export const BRAND_THEME_MAP: Record<string, string> = {
  // key = brand.id dari API (UUID) atau brand.slug kalau ada
  // value = data-brand attribute
  // Di-populate saat brands di-fetch dari GET /api/v1/brands
  // Fallback: nggak ada mapping → pakai EGG default (removeAttribute)
}

export function applyBrandTheme(brandSlug: string | null) {
  const root = document.documentElement
  if (!brandSlug) {
    root.removeAttribute('data-brand')
  } else {
    root.setAttribute('data-brand', brandSlug)
  }
}
```

### Theme Logic per Role
```
SPV / STAFF / FREELANCE:
  → Theme di-set saat login dari outlet yang di-assign
  → Locked, tidak bisa diganti user
  → applyBrandTheme(user.outletBrandSlug) dipanggil sekali setelah login

MANAGER / DIREKSI / ERP_OWNER / SUPER_ADMIN:
  → Default: removeAttribute (EGG holding theme)
  → Saat filter/pilih outlet tertentu di dashboard → applyBrandTheme(selectedBrandSlug)
  → Saat kembali ke overview (semua outlet) → applyBrandTheme(null)
```

  ke tabel brands saat ada brand baru atau kebutuhan self-service theming.
- **/change-password page**: firstLoginRequired flow (placeholder route cukup di F1)
- **Logout + clear httpOnly cookie**: koordinasi endpoint backend
- **Mobile responsive**: Tailwind ada, layout belum dioptimasi
